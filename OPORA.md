# Опора · 0.3

Локальное приложение для разработчика игр на Godot, работающего с Claude Code и Codex. Windows 10/11, x64. Интерфейс на русском, API-ключи не нужны.

## Что выяснили в аудите

Разработчик работает один, не программирует вручную и поручает агентам изменения в проекте целиком. Игры разных жанров, в том числе roguelike и incremental idle. Файлы лежат в папках; единый брендбук будет подготовлен позже. Главная проблема — мелкие противоречия в решениях и потеря общего понимания игры при работе с разными агентами.

Рабочая гипотеза: сначала нужен общий контекст, визуальные эталоны и понятные границы одной задачи. Генератор изображений без этой основы будет создавать новые варианты, но сам по себе не решит несогласованность. На реальном проекте гипотезу ещё нужно проверить.

## Запуск без программирования

1. Распакуйте **весь** архив `Opora-0.3.0-windows-x64.zip` или скачанный ZIP ветки и запустите `START-OPORA.cmd`. С версии 0.2 можно обновиться из программы.
2. Откройте папку `Opora-win32-x64` и запустите `Opora.exe`. Не переносите exe отдельно от остальных файлов.
3. Нажмите **Подключить проект** и выберите папку с `project.godot`.
4. У новой игры автоматически создаётся черновик брендбука. Проверьте источники и кандидаты в эталоны. У существующей игры используйте кнопку «Собрать брендбук из проекта» в разделе «Визуальный стиль». Заполните паспорт и постоянные замечания.
5. Добавьте одну небольшую задачу с критериями готовности и выберите её.
6. Откройте **Контекст для ИИ → Обновить файлы проекта**. Просмотрите изменения и запишите их.
7. Нажмите **Скопировать запрос** и вставьте его в Claude Code или Codex, работающий из корня этой игры. Для существующего чата явно попросите перечитать контекст.
8. Просмотрите результат в Godot. Новые замечания запишите в приложении и снова обновите контекст.

Последний подключённый проект открывается при следующем запуске. Переключаться между играми можно через выбор другой папки. До подключения показывается демонстрационная игра; её данные не переносятся в вашу игру.

## Где лежат данные

- `.opora/project.json` — паспорт, брендбук, задачи и статусы образцов, сохраняются автоматически.
- `.opora/references/` — копии выбранных изображений. Добавленные изображения сначала считаются кандидатами.
- `.opora/CONTEXT.md` — общая памятка для агентов, обновляется по кнопке.
- `AGENTS.md`, `CLAUDE.md` — небольшой блок Opora с указанием прочитать памятку. Остальной текст сохраняется.
- `.opora/backups/` — предыдущие версии файлов перед каждой синхронизацией.
- `.opora/agent-reports/` — отдельные отчёты агентов, не меняющие состояние задач.
- `.opora/config-backups/` — локальные копии настроек Claude перед изменением. Внутри создаётся `.gitignore`, поскольку чужие записи MCP могут содержать учётные данные.
- Демо сохраняется в локальном хранилище приложения. Настройка последней папки — в пользовательской папке Electron (`%APPDATA%/opora` при запуске из исходников; имя каталога в готовой сборке может отличаться).

Код, сцены, `project.godot` и ассеты за пределами `.opora` приложение не изменяет. Удаление образца из списка не удаляет его копию на диске. Символические ссылки на файлы записи не поддерживаются. Повреждённые или повторяющиеся маркеры блока Opora требуют ручного исправления; приложение не затирает такой файл.

Анализ проекта выполняется локально и не отправляет его файлы в сеть. Запросы к GitHub выполняются по кнопкам проверки и скачивания обновлений. Данные игры попадут к помощнику, когда вы разрешите ему читать папку или вставите скопированный текст в его чат. Папку `.opora` учитывайте при публикации Git-репозитория, в том числе резервные копии и изображения.

## Что делает автоматический брендбук

Читает `project.godot`, `.tscn`, `.tres`, `.gd`, `.svg`, находит объявления цветов (`Color`, `Color8`, строковые HEX и базовые именованные цвета), шрифты, размеры текста и параметры `StyleBoxFlat`. Для PNG/JPG/WebP выбирает до шести кандидатов, создаёт миниатюры и приблизительную палитру. Изображения и файлы шрифтов могут существовать в проекте, но не использоваться в игре; это явно отмечается.

Пропускает скрытые папки, `.godot`, `.git`, `.opora`, зависимости, сборки и символические ссылки. Лимиты: до 6000 файлов, до 32 МБ текста суммарно, до 2 МБ на текстовый файл и 4 МБ на выбранное изображение. Ограничения и пропуски отражаются в отчёте. Текст парсится без исполнения скриптов; импорт и запуск Godot не требуются. Повторное применение черновика не меняет невыбранные поля и не дублирует уже добавленные копии изображений.

Результат — черновик фактически найденных решений. Он не устанавливает художественное направление и не решает, какой из противоречащих вариантов правильный. Утверждение стиля и эталонов остаётся за пользователем. После правок обновите контекст для агентов обычной кнопкой.

## Встроенные обновления

Верхняя панель: **Обновления → Проверить обновления → Скачать обновление → Установить и перезапустить**. Версия 0.1 требует однократного ручного скачивания 0.2; далее функция уже есть в программе.

Канал: `https://raw.githubusercontent.com/Isedis/basket/opora/updates/latest.json`. Он содержит версию, точный SHA коммита, размеры и SHA256 частей. Программа скачивает части только из `Isedis/basket` по этому SHA, проверяет их и весь ZIP, перед установкой повторно проверяет архив. Переход на равную или более старую версию не выполняется.

Установка поддерживается в готовой Windows-сборке. Программа сохраняет изменения, распаковывает проверенный пакет, проверяет версию внутри него и запускает отдельный процесс PowerShell. Он ждёт закрытия Опоры, переносит старую папку в резервную, ставит новую и запускает её. Папки игр и пользовательская папка Electron не заменяются. При ошибке замены предусмотрена попытка восстановления. Результат записывается в `update-result.json` в пользовательской папке; ошибка показывается в окне обновлений. Резервная версия остаётся рядом с папкой приложения.

Установка и восстановление непосредственно на Windows в этой среде не проверены. Контрольные суммы защищают от повреждения загрузки, но не заменяют доверие к владельцу GitHub-репозитория. Установщик не отключает проверки TLS или политики выполнения PowerShell.

## Границы первой версии

- Это общая память проекта, не генератор графики.
- Нет автоматической оценки сходства, проверки сцен или управления терминалами агентов.
- Нет гарантии, что агент прочтёт или выполнит инструкции. Прямые новые указания пользователя имеют приоритет; конфликты следует явно обсуждать.
- Изменения формы сохраняются автоматически, но экспортированная памятка обновляется только по кнопке. Открытый чат сам обновления не получает.
- Одновременное редактирование одной папки из нескольких экземпляров приложения не поддерживается.
- Бинарник не подписан сертификатом издателя. Запуск именно в Windows пока не проверен: сборка и проверки выполнены в Linux.

## Подключение из терминала через MCP

Откройте **Агенты · MCP → Настроить подключение → Добавить подключение** для выбранного клиента. Перезапустите Claude Code или Codex в папке игры. При запросе разрешений подтвердите сервер в самом клиенте. Можно скопировать первый запрос со страницы подключения. Статус «Настроено» подтверждает только запись настроек.

Claude получает запись в проектном `.mcp.json`. Codex получает запись с отдельным именем `opora-<идентификатор>` в пользовательском `config.toml`; существующий `CODEX_HOME` учитывается. Дописывается управляемый блок, остальной текст TOML и комментарии сохраняются. Повторная настройка обновляет только этот блок; конфликтующая ручная запись или некорректный файл не затираются. Перед изменением сохраняется копия; копии Codex лежат в его пользовательской папке `opora-backups`, вне игры. Содержимое чужих настроек не выводится в интерфейс. Проектный `.mcp.json` содержит абсолютные пути машины: учитывайте это при передаче проекта другому пользователю.

Транспорт — локальный stdio. Клиент запускает `Opora.exe` с `ELECTRON_RUN_AS_NODE=1` и входной точкой `resources/app.asar/mcp/server.cjs`, передавая корень игры аргументом. Открытого порта, сервера в интернете и дополнительного Node.js нет. Окно Опоры может быть закрыто: сервер читает последнюю сохранённую `.opora/project.json` при каждом запросе. Несохранённые правки не видны. При переносе игры или приложения настройте подключение заново; ненужные старые записи Codex можно удалить его командой `codex mcp remove <имя>`.

Инструменты: `opora_get_project`, `opora_get_context`, `opora_get_brandbook`, `opora_list_tasks`, `opora_get_reference`, `opora_list_reports`, `opora_report_progress`. Первый возвращает путь и `project_id`; агент обязан проверить соответствие своему проекту. Следующие требуют этот ID. Для изображения и отчёта требуется актуальная `revision`. Изменение правил, задач или брендбука меняет её, и запись со старым контекстом отклоняется. Идентификатор зависит от физической папки, поэтому копия игры в другой папке получает другой ID.

Отчёт может иметь статус «в работе», «нужна помощь» или «готово к просмотру». Переданные результаты проверок — заявления агента. Опора не запускала Godot и не подтверждает их самостоятельно. Запись отчёта не меняет `.opora/project.json`, статус задачи или утверждение брендбука. Повтор одного `request_id` с теми же данными не создаёт дубликат; изменение содержимого требует нового ID. Страница агентов обновляет отчёты каждые три секунды, пока открыта. Отмечается, если контекст после отчёта изменился.

Авторизация модели остаётся в Claude/Codex. Наличие MCP не гарантирует, что модель вызовет инструмент: начните с явного запроса прочитать Опору. Проверено взаимодействие SDK-клиента и stdio-сервера, а не полноценный сеанс модели с пользовательской подпиской.

## Разработка

Node.js 22.12+ и npm. Исходники: `desktop/` — Electron, `ui/` — интерфейс и общий формат контекста, `src/` — операции с проектом.

```sh
npm ci
npm start
npm run check
npm test
npm run test:ui
npm run test:desktop
npm run test:mcp
npm run package:win
```

В среде с HTTPS-прокси загрузчик Electron поддерживает `ELECTRON_GET_USE_PROXY=true`; сохраняйте настроенные CA и проверку TLS. Если при установке был указан `ELECTRON_SKIP_BINARY_DOWNLOAD=1`, перед `npm start` выполните `node node_modules/electron/install.js` с доступом к официальным загрузкам Electron.

`npm test` запускает 28 проверок: проект, брендбук, обновления, привязка MCP к папке, актуальность контекста, отдельные отчёты и сохранность настроек клиентов.

`npm run test:ui` требует установленный Chromium (по умолчанию `/usr/bin/chromium`, другой путь задаётся через `CHROMIUM_PATH`). Проверяет демо и интерфейс с адаптером к реальным временным файлам проекта. Диалоги Windows и нативный Electron этим тестом не проверяются. Снимки экрана пишутся в `artifacts/`.

`npm run test:desktop` проверяет настоящее окно Electron, preload/IPC, копирование и чтение эталонов, синхронизацию инструкций, нативный буфер обмена, сохранение при закрытии и восстановление последнего проекта при повторном запуске. Выбор папки и изображения подставляется тестом вместо ручного диалога. В Linux используется headless-режим; флаг `--no-sandbox` применяется только в тестовом запуске. Обычный запуск приложения его не использует.

Также проверяется автоматический брендбук и выборочное обновление полей. Запрос проверки версии проходит через сетевой стек Electron с изолированным тестовым HTTPS-ответом. UI скачивания и установки тестируется с адаптером; реальная замена Windows-приложения этим тестом не проверяется.

`npm run test:mcp` поднимает настоящий stdio-сервер и подключается официальным MCP SDK-клиентом: инициализация, 7 инструментов, свежий контекст, отказы при другом проекте/старой версии и сохранение отчёта. `OPORA_MCP_EXECUTABLE` и `OPORA_MCP_ENTRY` позволяют проверить тот же сервер через Electron в режиме Node и из упакованного app.asar. `test:desktop` дополнительно создаёт временную настройку Claude, запускает её MCP-процесс, читает изображение и показывает полученный отчёт в интерфейсе. Пользовательские глобальные настройки в тестах не изменяются.

### Публикация следующей версии

Обновите версию в `package.json`, `package-lock.json` и интерфейсе, выполните проверки, затем `npm run package:win` и `python scripts/prepare-git-download.py`. Скрипт создаёт Windows ZIP, демо и части архива меньше 50 МиБ. Закоммитьте исходники и части. Затем выполните `node scripts/update-channel.cjs`: он создаст `updates/latest.json`, указывающий на этот неизменяемый коммит. Закоммитьте метаданные и загрузите оба коммита в ветку `opora`. Старые части должны оставаться доступны в истории. Готовая сборка исключает служебные папки с частями и каналом обновлений.

Для чтения интерфейса без Electron можно открыть `ui/index.html` в браузере: это только демо, без подключения папок. Используйте существующий checkout; Git worktree для приложения не требуется.

## Следующий этап аудита

На одной реальной игре собрать 5–10 типичных замечаний и 2–3 утверждённых образца. Выполнить несколько сопоставимых задач с общей памяткой и записать, сколько правок пришлось повторять. Это покажет, что добавлять дальше: извлечение темы Godot, проверку палитры/шрифтов или подготовку запросов для генерации ассетов.
