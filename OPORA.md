# Опора · 0.13.0

Локальное приложение для разработчика игр на Godot, работающего с Claude Code и Codex. Windows 10/11, x64. Интерфейс на русском, API-ключи не нужны.

## Что выяснили в аудите

Разработчик работает один, не программирует вручную и поручает агентам изменения в проекте целиком. Игры разных жанров, в том числе roguelike и incremental idle. Файлы лежат в папках; единый брендбук будет подготовлен позже. Главная проблема — мелкие противоречия в решениях и потеря общего понимания игры при работе с разными агентами.

Рабочая гипотеза: сначала нужен общий контекст, визуальные эталоны и понятные границы одной задачи. Генератор изображений без этой основы будет создавать новые варианты, но сам по себе не решит несогласованность. На реальном проекте гипотезу ещё нужно проверить.

## Запуск без программирования

1. [Скачайте готовую Опору для Windows](https://github.com/Isedis/basket/releases/download/v0.13.0/Opora-Windows.zip).
2. Полностью распакуйте архив в новую папку.
3. Откройте папку `Opora-win32-x64` и запустите `Opora.exe`.
4. Если игра не открылась автоматически, нажмите «Открыть проект» и выберите её папку с `project.godot`.
5. Пометки, задачи и брендбук хранятся в `.opora` внутри папки игры и остаются доступными в новой Опоре.

Следующие обновления устанавливаются через «Обновления → Проверить и обновить» в приложении.

## Терминальный интерфейс и быстрые клавиши

В 0.6 используются плоские рамки, панельные заголовки, инверсное выделение навигации и фиксированная строка состояния. Рабочая область прокручивается отдельно. Шапка показывает текущий раздел, боковая панель — выбранную задачу, нижняя строка — режим, статус брендбука и реальное состояние сохранения.

`Ctrl+K` открывает поиск по 12 действиям приложения. Русские названия и английские слова (`/tasks`, `/brand`, `/save`, `copy`) фильтруют список; стрелки выбирают строку, Enter выполняет действие, Escape закрывает список. Поддерживаются навигация, создание задачи, копирование запроса, разбор брендбука, открытие/сохранение проекта, обновления и справка. Команды вызывают те же локальные функции интерфейса. Меню не открывается поверх формы задачи или подготовки брендбука. [Рабочий стол](docs/terminal-workspace.png) · [Меню команд](docs/terminal-commands.png).


Интерфейс оформлен по предоставленному брендбуку Isidacorp: `#000000`, `#FFF2CC`, акцент `#FF0000`, вспомогательные `#10120F` и `#92988D`. JetBrains Mono 400/600 включён локально по [SIL OFL](ui/fonts/OFL.txt), без загрузки с CDN. В компактной шапке используется допустимое текстовое имя студии. Дизайн Опоры не подменяет брендбук подключённой игры.

Порядок разделов: рабочий стол, задачи, брендбук, агенты, контекст. Вверху рабочего стола находится выбранная задача; паспорт и постоянные правила остаются ниже. При достаточной ширине поля стиля и разбор видны рядом. Источники, технические подробности и остальные замечания раскрываются по нажатию.

| Клавиши | Действие |
| --- | --- |
| Ctrl+K | Открыть или закрыть команды |
| Ctrl+1…5 | Перейти в раздел |
| Ctrl+N | Создать задачу |
| Ctrl+S | Сохранить |
| Ctrl+Enter | Сохранить задачу в диалоге; скопировать запрос в «Контексте» |
| F1 | Открыть справку |

Формы также сохраняются автоматически. `Opora-demo.html` содержит шрифт внутри файла и открывается без сети.

## Где лежат данные

- `.opora/project.json` — паспорт, брендбук, задачи и статусы образцов, сохраняются автоматически.
- `.opora/references/` — копии выбранных изображений. Добавленные изображения сначала считаются кандидатами.
- `.opora/CONTEXT.md` — общая памятка для агентов, обновляется по кнопке.
- `AGENTS.md`, `CLAUDE.md` — небольшой блок Opora с указанием прочитать памятку. Остальной текст сохраняется.
- `.opora/backups/` — предыдущие версии файлов перед каждой синхронизацией.
- `.opora/agent-reports/` — отдельные отчёты агентов, не меняющие состояние задач.
- `.opora/config-backups/` — локальные копии настроек Claude перед изменением. Внутри создаётся `.gitignore`, поскольку чужие записи MCP могут содержать учётные данные.
- Демо сохраняется в локальном хранилище приложения. Настройка последней папки — в пользовательской папке Electron (`%APPDATA%/opora` при запуске из исходников; имя каталога в готовой сборке может отличаться).

Код, сцены, `project.godot` и ассеты за пределами `.opora` приложение не изменяет. Удаление образца из списка не удаляет его копию на диске. Символические ссылки на файлы записи не поддерживаются. Повреждённые или повторяющиеся маркеры блока Opora требуют ручного исправления; приложение не затирает такой файл.

Анализ проекта выполняется локально и не отправляет его файлы в сеть. Запросы к GitHub выполняются по кнопкам проверки и скачивания обновлений. Данные игры попадут к помощнику, когда вы разрешите ему читать папку или вставите скопированный текст в его чат. Папку `.opora` учитывайте при публикации Git-репозитория, в том числе резервные копии и изображения.

## Что делает автоматический брендбук

Читает `project.godot`, `.tscn`, `.tres`, `.gd`, `.svg`, находит объявления цветов (`Color`, `Color8`, строковые HEX и базовые именованные цвета), шрифты, размеры текста и параметры `StyleBoxFlat`. Для PNG/JPG/WebP выбирает до шести кандидатов, создаёт миниатюры и приблизительную палитру. Изображения и файлы шрифтов могут существовать в проекте, но не использоваться в игре; это явно отмечается.

Пропускает скрытые папки, `.godot`, `.git`, `.opora`, зависимости, сборки и символические ссылки. Лимиты: до 6000 файлов, до 32 МБ текста суммарно, до 2 МБ на текстовый файл и 4 МБ на выбранное изображение. Ограничения и пропуски отражаются в отчёте. Текст парсится без исполнения скриптов; импорт и запуск Godot не требуются. Повторное применение черновика не меняет невыбранные поля и не дублирует уже добавленные копии изображений.

Результат — черновик фактически найденных решений. Он не устанавливает художественное направление и не решает, какой из противоречащих вариантов правильный. Утверждение стиля и эталонов остаётся за пользователем. После правок обновите контекст для агентов обычной кнопкой.

## Встроенные обновления

Верхняя панель: **Обновления → Проверить обновления → Скачать обновление → Установить и перезапустить**. Версия 0.1 требует однократного ручного скачивания 0.2; далее функция уже есть в программе.

Канал: `https://raw.githubusercontent.com/Isedis/basket/opora/updates/latest.json`. Он содержит версию, точный SHA коммита, размеры и SHA256 частей. Программа скачивает части только из `Isedis/basket` по этому SHA, проверяет их и весь ZIP, перед установкой повторно проверяет архив. Переход на равную или более старую версию не выполняется.

Установка поддерживается в готовой Windows-сборке. Программа проверяет запись в родительскую папку приложения и активные MCP-сессии. Архив распаковывается в соседний `.opora-update-*`, на том же диске, что и приложение; версия читается из настоящего ASAR, критические файлы получают SHA256. PowerShell запускается с рабочей папкой внутри этого задания, вне заменяемой копии. Окно Опоры закрывается только после сигнала готовности от этого процесса с правильными токеном и PID. При ошибке запуска помощника приложение остаётся открытым, задание получает флаг отмены.

Помощник ждёт завершения старой Опоры и процессов из её папки, сохраняет прежнюю копию, перемещает подготовленную папку на место и запускает exe по тому же пути. Новая Опора после загрузки окна записывает подтверждение со своей версией, путём, PID и токеном задания. Только после этого результат становится `installed`. При отказе запуска или преждевременном выходе предусмотрено восстановление старой папки и повторное открытие. При живом процессе без подтверждения новая папка остаётся на месте, чтобы не заменять работающие файлы; результат — `needs_attention`, обе копии сохраняются.

Результат хранится в пользовательском `update-result.json`; этапы и stderr/stdout — в папке задания рядом с приложением. При ошибке после закрытия GUI помощник пытается показать сообщение Windows. В «Обновлениях» доступны причина, текущая папка и копирование диагностики. Папки игр и пользовательская папка Electron не заменяются. Процессы не завершаются принудительно. Старые ярлыки на другую копию exe не меняются.

Установка и восстановление непосредственно на Windows в этой среде не проверены. Контрольные суммы защищают от повреждения загрузки, но не заменяют доверие к владельцу GitHub-репозитория. Установщик не отключает проверки TLS или политики выполнения PowerShell.

## Оценка правил брендбука

Раздел **Брендбук → Разбор** даёт объяснимую проверку 9 пунктов и подсказки. Она работает локально, без модели и API-ключа. Показатель N/9 — число пунктов с достаточными данными. Это не оценка художественного качества и не подтверждение соответствия игры WCAG.

Проверяются наличие конкретного направления, корректность HEX, назначение цветов, читаемость явно заявленных пар, выбор шрифта, размеры/роли текста, утверждённые доступные образцы, принятые ограничения и статус утверждения. Автоматические сообщения «назначение не утверждено», «настроение не установлено» и общие предложенные ограничения не выдаются за принятые решения. Маленький пиксельный шрифт сам по себе не считается ошибкой.

Пары задаются строкой `Основной текст: #FFFFFF на #151E21`, либо отдельными однозначными цветами текста и фона. Для явно указанного `Крупный текст: ... на ...` ориентир 3:1, в остальных случаях 4.5:1. Это расчёт по относительной яркости sRGB, основанный на [WCAG Contrast Minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html). Фактический размер, подложка и отображение в игре не определяются. Полупрозрачные цвета без известного результата наложения остаются непроверенными. Случайные сочетания палитры не проверяются как реальные текстовые пары. Явно отмеченный disabled / неактивный текст не оценивается по порогу обычного текста; исключение отмечается в разборе. Предлагаемый цвет сначала берётся из существующей палитры, а новые белый/чёрный предлагаются только как варианты на согласование.

Файловая проверка читает доступность первых 64 образцов; содержимое изображений не оценивается. Пустые, отсутствующие и недоступные файлы отмечаются. Файл больше 8 МиБ может быть доступен в интерфейсе, но не через MCP image-tool; это отмечается отдельно. На каждое поле проверяется до 64 КБ текста, до 256 цветовых записей и 20 пар; достижение ограничений видно в разборе.

Замечание можно превратить в задачу или перейти к соответствующему полю. Одна незавершённая задача на одно замечание не дублируется. Исправление правил остаётся предложением, утверждаемым пользователем; разбор сам ничего не меняет и не помечает задачи завершёнными. При правке полей замечания пересчитываются. Есть копирование разбора и MCP-инструмент `opora_review_brandbook`, который читает сохранённую версию проекта. После обновления приложения перезапустите MCP-сессию для появления нового инструмента.

## Границы первой версии

- Это общая память проекта, не генератор графики.
- Нет автоматической оценки сходства, проверки сцен запуском Godot или управления терминалами агентов. Карта показывает статические связи файлов.
- Нет гарантии, что агент прочтёт или выполнит инструкции. Прямые новые указания пользователя имеют приоритет; конфликты следует явно обсуждать.
- Изменения формы сохраняются автоматически, но экспортированная памятка обновляется только по кнопке. Открытый чат сам обновления не получает.
- Одновременное редактирование одной папки из нескольких экземпляров приложения не поддерживается.
- Бинарник не подписан сертификатом издателя. Запуск именно в Windows пока не проверен: сборка и проверки выполнены в Linux.

## Подключение из терминала через MCP

Откройте **Агенты → Настроить подключение → Добавить подключение** для выбранного клиента. Перезапустите Claude Code или Codex в папке игры. При запросе разрешений подтвердите сервер в самом клиенте. Можно скопировать первый запрос со страницы подключения. Статус «Настроено» подтверждает только запись настроек.

Claude получает запись в проектном `.mcp.json`. Codex получает запись с отдельным именем `opora-<идентификатор>` в пользовательском `config.toml`; существующий `CODEX_HOME` учитывается. Дописывается управляемый блок, остальной текст TOML и комментарии сохраняются. Повторная настройка обновляет только этот блок; конфликтующая ручная запись или некорректный файл не затираются. Перед изменением сохраняется копия; копии Codex лежат в его пользовательской папке `opora-backups`, вне игры. Содержимое чужих настроек не выводится в интерфейс. Проектный `.mcp.json` содержит абсолютные пути машины: учитывайте это при передаче проекта другому пользователю.

Транспорт — локальный stdio. Клиент запускает `Opora.exe` с `ELECTRON_RUN_AS_NODE=1` и входной точкой `resources/app.asar/mcp/server.cjs`, передавая корень игры аргументом. Открытого порта, сервера в интернете и дополнительного Node.js нет. Окно Опоры может быть закрыто: сервер читает последнюю сохранённую `.opora/project.json` при каждом запросе. Несохранённые правки не видны. При переносе игры или приложения настройте подключение заново; ненужные старые записи Codex можно удалить его командой `codex mcp remove <имя>`.

Инструменты: `opora_get_work_context`, `opora_read_project_field`, `opora_get_project`, `opora_list_feedback`, `opora_get_feedback_image`, `opora_submit_feedback_result`, `opora_get_project_map`, `opora_get_context`, `opora_get_brandbook`, `opora_review_brandbook`, `opora_update_brandbook`, `opora_update_project`, `opora_list_tasks`, `opora_get_reference`, `opora_list_reports`, `opora_report_progress`. Первый возвращает путь и `project_id`; агент обязан проверить соответствие своему проекту. Следующие требуют этот ID. Для изображения и отчёта требуется актуальная `revision`. Изменение правил, задач или брендбука меняет её, и запись со старым контекстом отклоняется. Идентификатор зависит от физической папки, поэтому копия игры в другой папке получает другой ID.

Отчёт может иметь статус «в работе», «нужна помощь» или «готово к просмотру». Переданные результаты проверок — заявления агента. Опора не запускала Godot и не подтверждает их самостоятельно. Запись отчёта не меняет `.opora/project.json`, статус задачи или утверждение брендбука. Повтор одного `request_id` с теми же данными не создаёт дубликат; изменение содержимого требует нового ID. Страница агентов обновляет отчёты каждые три секунды, пока открыта. Отмечается, если контекст после отчёта изменился.

Авторизация модели остаётся в Claude/Codex. Наличие MCP не гарантирует, что модель вызовет инструмент: начните с явного запроса прочитать Опору. Проверено взаимодействие SDK-клиента и stdio-сервера, а не полноценный сеанс модели с пользовательской подпиской.

## Разработка

Node.js 22.12+ и npm. Исходники: `desktop/` — Electron, `ui/` — интерфейс и общий формат контекста, `src/` — операции с проектом.

```sh
npm ci
npm start
npm run check
npm test
npm run test:ui
npm run test:desktop
npm run test:mcp
npm run test:launcher
npm run test:installer
npm run test:restart
npm run package:win
```

В среде с HTTPS-прокси загрузчик Electron поддерживает `ELECTRON_GET_USE_PROXY=true`; сохраняйте настроенные CA и проверку TLS. Если при установке был указан `ELECTRON_SKIP_BINARY_DOWNLOAD=1`, перед `npm start` выполните `node node_modules/electron/install.js` с доступом к официальным загрузкам Electron.

`npm test` запускает 81 проверку: проект, брендбук, разбор правил/контраст, обновления, привязка MCP, актуальность контекста, отдельные отчёты и сохранность настроек клиентов.

`npm run test:launcher` требует Windows PowerShell 5.1 или PowerShell 7 (`pwsh` в Linux, другой путь через `OPORA_PWSH`). Выполняет 13 сценариев с настоящими ZIP, SHA256, файловыми блокировками и откатом: первый/повторный запуск, частичная установка, повреждённые данные, ошибка переноса и запуска, параллельные запускатели, более новая версия, открытый MCP, защита от второго окна и недопустимый путь в архиве. Запуск GUI, список процессов Windows и чтение версии exe в этих сценариях подставляются тестом. Отдельно сверяется встроенный в CMD код с проверенным исходником и выполняется его PowerShell-команда: ошибка обязана вернуть код 1 и оставить диагностический журнал. Проверки выполнены с PowerShell 7 в Linux; запуск через настоящий cmd.exe / PowerShell 5.1 на Windows здесь не проверен.

`npm run test:ui` требует установленный Chromium (по умолчанию `/usr/bin/chromium`, другой путь задаётся через `CHROMIUM_PATH`). Проверяет демо и интерфейс с адаптером к реальным временным файлам проекта, поиск команд, клавиатурную навигацию, пустую выдачу, повторное открытие и сохранность открытой формы задачи. ## Запись брендбука агентом — 0.7

MCP `opora_update_brandbook` требует `project_id`, актуальную `revision`, `agent` (claude/codex/other), уникальный `request_id`, краткий `summary` и непустой объект `fields`. Поля: direction, palette, fonts, avoid, каждое до 64 000 символов. Передаются только изменяемые поля; остальные сохраняются. Пустая строка явно очищает поле. Статус, изображения и задачи через этот инструмент не записываются. Статус после новой записи всегда draft. Источники и объяснения указываются агентом в тексте и summary, не являются независимой проверкой.

Сервер проверяет проект и ревизию под общей межпроцессной блокировкой, сохраняет предыдущий project.json в `.opora/backups/brandbook-*.json`, затем атомарно записывает новое состояние. Возвращаются новые revision и brand_revision, брендбук и путь резервной копии. Точный повтор последнего запроса не повторяет запись и не отменяет ручное утверждение; другой payload под тем же request_id отклоняется. После другого изменения агенту может понадобиться перечитать контекст и использовать новый request_id. Старая ревизия отклоняется до записи.

Автосохранение GUI использует трёхстороннее объединение данных проекта: базовая сохранённая версия, ручная версия и версия на диске. Непересекающиеся правки объединяются. При разном изменении одного поля или утверждении невиденных изменений сохранение останавливается; интерфейс сохраняет локальный текст и предлагает сравнить версии. Синхронизация AGENTS/CLAUDE/CONTEXT не записывает устаревший предпросмотр. Памятка в файлах обновляется по кнопке, MCP читает актуальную версию сразу.

Блокировка proper-lockfile общая для сохранения, экспорта и MCP. Зависшие блокировки после аварийного завершения освобождаются по сроку 30 секунд; активные обновляют heartbeat. Открытый GUI читает изменения каждые две секунды, сохраняя ввод пользователя. Прямое редактирование project.json сторонними программами не использует этот протокол и не поддерживается. При конфликте выбирается локальная или сохранённая версия конфликтующих полей; непересекающиеся изменения объединяются.

Проверки: прямой SDK-вызов, два отдельных MCP-процесса с одной ревизией, отказ при устаревших данных, сохранность задач/эталонов, резервная копия, точный повтор и ручное утверждение. В настоящем Electron проверены копирование запроса, появление полей без перезапуска окна и конфликт реального MCP с задержанным автосохранением; пользовательский выбор разрешает конфликт. Проверено в Linux; отдельная сессия модели под пользовательской подпиской и Windows здесь не проверялись.

## Заполнение всей Опоры и экономия контекста — 0.7

`opora_update_project` использует ту же привязку проекта, проверку revision, блокировку, резервную копию и повтор запроса. В fields доступны name, genre, pitch, experience, goal, pillars, rules, brand (direction/palette/fonts/avoid), tasks, active_task_id и reference_files. Задачи добавляются или обновляются по id; пропущенные записи сохраняются. Агент задаёт backlog/active; изменённая завершённая задача открывается заново. Утверждение стиля/изображений и завершение задач остаются ручными.

reference_files — относительные пути PNG/JPEG/WebP внутри игры: до 20 файлов, до 8 МиБ каждый и 32 МиБ суммарно. Копии попадают в .opora/references как кандидаты. Обход родительских папок, абсолютные пути и символические ссылки запрещены; оригиналы не заменяются. Общий project.json ограничен 2 МиБ. Возвращаются сохранённое состояние и новая revision.

`opora_get_context(project_id, known_revision?)` использует до 8 снимков на MCP-процесс. Без известной версии — mode full с прежним читаемым markdown. С совпадающей известной версией — mode unchanged без повторного текста. При изменении — mode delta, changes с полными заменами полей и removed со списком удалённых ключей; массивы передаются целиком. Выбор другой задачи передаёт tasks с критериями. Если дельта превышает 256 КБ или снимок потерян, возвращается полный контекст. Это экономит повторную передачу неизменных данных; не сокращает права, проверки актуальности или доступ к полному контексту. После потери истории чата нужно убрать known_revision.

Проверены полный/неизменённый/изменённый контекст, потеря кеша, неправильный проект, запись всех данных, отклонение завершения задачи и недопустимого пути. Нативный Electron подхватывает паспорт, задачи и кандидаты из MCP.

## Карта проекта — 0.8

Раздел «Карта проекта» (Ctrl+6) показывает инвентарь и окружение выбранного файла: кто на него ссылается и на что ссылается он. Карточки содержат тип файла, путь и исходную строку связи; доступны поиск по пути/class_name, фильтры, страницы по 40 записей, главная сцена и копирование снимка агенту. Карта обновляется при открытии раздела и по кнопке; время сканирования видно на экране.

MCP opora_get_project_map принимает project_id, необязательные file, query, kind, offset, limit (1–100). Без file возвращает страницу инвентаря и сводку. С file — входящие/исходящие связи, до 32 имён функций/сигналов GDScript, class_name и неразрешённые пути. Для каждой стороны связей offset/limit применяются отдельно, полное число видно в incoming_total/outgoing_total. map_revision относится к файлам игры и не заменяет revision контекста Опоры. Инвентарь и соседние карточки не дублируют списки символов и хеши файлов.

Читаются явные res:// и uid://, пути extends/preload/load, заголовки сцен/ресурсов, sidecar .uid, главная сцена и автозагрузки. Разрешается наследование локального class_name. Комментарии и тройные строки GDScript не становятся ссылками. Составные load-выражения отмечаются как динамические. Строковые пути в коде — свидетельство наличия пути, не доказательство вызова. Произвольные обращения к глобальным классам/автозагрузкам, сгенерированные пути и содержимое двоичных сцен не восстанавливаются. UID из пропущенного .godot/uid_cache.bin может остаться неразрешённым.

Сканирование локальное, без записи в проект и без запуска Godot. Пропускаются скрытые папки, сборки, зависимости и символические ссылки; addons остаются в карте. Ограничения: 6000 файлов, 18000 записей обхода, глубина 40, 2 МиБ на текстовый файл, 32 МиБ текста суммарно, 24000 связей, до 1024 явных ссылок из одного файла. Достигнутые ограничения помечают карту неполной. Доступность целей вне индекса проверяется отдельно; они не объявляются отсутствующими только из-за лимита.

В памяти процесса хранятся разобранные данные трёх последних проектов. Каждый запрос сверяет метаданные файлов (размер, mtime, ctime), повторно разбираются изменённые тексты. После перезапуска кеш собирается заново. Одновременные запросы одного проекта используют общий проход. Ответ MCP ограничен 256 КБ; уменьшите limit при превышении. Карта — снимок во время сканирования: перед правкой агент должен читать актуальный исходник.

Проверены направления связей и строки, UID и главная сцена, автозагрузки, наследование, динамические загрузки, фильтры и страницы, повторное использование кеша, изменения/удаления, неполный обход и символические ссылки. SDK проверяет карту и отказы при чужом проекте/небезопасном пути. Нативный Electron проверяет поиск, переходы, буфер обмена и появление отсутствующего файла после обновления.

## Замечания на снимках — 0.9

Раздел «Замечания» (Ctrl+7): снимки из файла или системного буфера, прямоугольники мышью в нормализованных координатах x/y/w/h (0–1), тип fix/keep, текст и необязательный путь к сцене. «Весь экран» позволяет оставить замечание без мыши. Запись выполняется явной кнопкой. Черновик формы сохраняется в памяти при переходах между разделами одной открытой игры; несохранённую форму нужно сохранить до закрытия приложения или смены проекта.

Данные отдельно от project.json: .opora/visual-feedback.json и неизменяемые копии PNG в .opora/feedback-images/. Общая блокировка с сохранением проекта, атомарная замена JSON, резервные версии .opora/backups/feedback-*.json. SHA256 проверяется при чтении изображения; точные повторы снимков и одинаковые нормализованные комментарии того же типа/сцены в близкой области не дублируются. Смысловое объединение нейросетью не выполняется.

Три статуса: open, ready, accepted. Результат агента переводит связанные замечания в ready. Пользователь принимает последнюю версию либо возвращает замечание с причиной. Снимки прошлых результатов и история решений сохраняются. Принятые keep — предпочтения пользователя; это не автоматическое утверждение брендбука или завершение задачи. Принятые замечания агент изменять не может. Позднее принятие устаревшей версии отклоняется, как и запись с устаревшей feedback_revision. При точном повторе результата под прежним request_id ручное решение не отменяется.

MCP opora_list_feedback: project_id и необязательные shot_id/note_id/offset/limit. Без shot_id — страницы сводок снимков; с shot_id — страницы замечаний с последними 8 событиями истории и связанными результатами; с note_id — страницы полной истории этого замечания. limit 1–50. opora_get_feedback_image возвращает исходный PNG либо result_id, описание выбранного note_id и его исходные пиксельные координаты. Прямоугольник не рисуется в PNG для агента: область задаётся отдельными координатами. Они относятся к оригиналу; новый результат может иметь другую компоновку.

MCP opora_submit_feedback_result: project_id, актуальная feedback_revision, shot_id, note_ids, image_file (относительный PNG внутри игры), agent, request_id и summary. Произвольные пути, обход родительских папок и символические ссылки запрещены. Инструмент возвращает новый feedback_revision и result_id, не подтверждает качество результата. Запуск игры и получение нового снимка выполняет агент/пользователь; Опора не снимает игру автоматически. Инструкции MCP и общий контекст направляют агента читать замечания перед изменением UI. Ручной запрос из раздела и связанная задача содержат нужные идентификаторы.

Ограничения: 200 снимков, 200 замечаний и 30 результатов на снимок, 100 событий на замечание, JSON до 2 МиБ. Копия PNG до 8 МиБ и 16 миллионов пикселей; импорт PNG/JPEG/WebP и буфера нормализуется Electron в PNG. MCP принимает готовый PNG. Ответы списков до 256 КБ: уменьшите limit или выберите note_id. Изображения могут содержать личные данные — они остаются в папке проекта и попадают агенту при чтении; учитывайте это при публикации .opora.

Проверены координаты, дубли, отдельное хранение, резервные копии, конкурентные записи, устаревшие версии, повреждённые изображения и запрещённые пути. В реальном Electron: файл и ClipboardItem API Electron 45, выделение мышью, создание задачи без дубля, копирование запроса, результат через настоящий MCP, сравнение, возврат, повторный результат, принятие, ручное добавление результата и восстановление после перезапуска. Проверки выполнены в Linux; Windows здесь не проверен.

## Исправления аудита и общий рабочий контекст — 0.10

Текущая версия расширяет описанное выше поведение 0.9. Старые project.json и visual-feedback.json читаются без ручной миграции. Перед изменениями сохраняются резервные версии.

opora_get_work_context(project_id?, task_id?, file?, known_revision?, limit?) — один пакет с идентификатором/путём проекта, паспортом, брендбуком, выбранной задачей, относящимися к ней решениями/замечаниями, соседними файлами и версиями всех источников. Без project_id можно начать сеанс, затем обязательно проверить root. known_revision — work_revision прошлого сохранённого в чате пакета. Кеш до 8 версий; после перезапуска/потери контекста возвращается полный пакет. Набор связанных данных читается с повторной проверкой ревизий метаданных; при постоянном редактировании возвращается BUSY_CONTEXT. Исходники при сканировании не блокируются.

Сокращения помечены length/truncated/read_more. opora_read_project_field читает строки паспорта/брендбука и task.title/task.acceptance с task_id, offset и limit до 32000 UTF-16 единиц. opora_list_tasks имеет task_id/status/offset/limit; критерии больше 8000 символов явно сокращаются. opora_get_brandbook сокращает длинные поля с указанием полного чтения, references имеет страницы. opora_update_project по умолчанию возвращает подтверждение и изменённые поля; include_state=true включает полное состояние. У задач допускаются feedback_note_id/feedback_shot_id с проверкой пары в том же проекте.

Обычный opora_get_context сравнивает размер дельты с полным читаемым контекстом и выбирает меньший допустимый ответ. Дельта всё ещё заменяет массивы целиком. Полный читаемый контекст не содержит критерии всех невыбранных задач: они доступны через список/чтение поля.

Сохранение GUI, MCP и экспорт используют одинаковый лимит project.json 2 МиБ. Ручное редактирование поля стиля снимает approved; core.saveProject также проверяет изменение содержимого. Явное подтверждение передаёт точные четыре поля, которые пользователь рассмотрел. approval содержит SHA256 содержимого и время. Старое approved сохраняет прежний смысл при чтении; новое подтверждение получает привязку к содержимому.

Карта хранит до 1024 функций/сигналов каждого типа на файл с полным счётчиком, symbols_limited и страницами symbol_offset/symbol_limit/symbol_query. GUI имеет кнопки страниц символов. Добавлены ссылки на известные глобальные классы при создании экземпляра/обращении к членам и типам. Это статические кандидаты, а не анализ областей видимости или полная модель выполнения; построенные кодом Control-узлы не восстанавливаются.

Примечания имеют scope=region/scene/project. Принятое keep с supersedes помечает старое решение superseded_by, сохраняя историю. Списки по умолчанию исключают заменённые решения и закрытые обсуждения; include_superseded/include_archived возвращают их. Фильтры status/scene/scope/query позволяют избежать обхода всех снимков. Общий пакет включает связанное замечание, keep того же снимка, подходящие решения сцены и принятые действующие project-решения. Разные статусы задачи и замечания показаны как предупреждения; принятие изображения не завершает задачу автоматически.

feedback_revision сохраняет общую защиту. note_revisions — словарь ID → версия затронутого замечания. При отправке результата/ручном решении с этими токенами разрешается безопасное объединение с изменениями других замечаний; изменение целевой записи отклоняется. Заменяющее решение требует проверки общей версии.

Старые результаты и события автоматически выносятся в .opora/feedback-archives/<sha256>.json с проверкой хеша. В активном состоянии остаются последние результаты для каждого замечания, несколько последних попыток и 8 последних событий; request_id-квитанции сохраняют идемпотентность после архивации. opora_list_feedback с note_id читает полную историю и результаты страницами, включая архивы; изображения старых result_id доступны прежним инструментом. GUI загружает старые версии через историю. «Закрыть обсуждение» скрывает его, но сохраняет принятые решения и позволяет восстановить.

Текущий файл замечаний ограничен 8 МиБ, активных обсуждений 200 (всего с закрытыми до 2000), заметок на снимок 200; старый предел 30 результатов заменён архивированием. Архивы и резервные копии сохраняются на диске; их общий размер не ограничивается автоматически. Программа не удаляет историю ради освобождения места. Исходные PNG по-прежнему до 8 МиБ/16M пикселей.

source_snapshot включает SHA256 версии статических файлов проекта, сцен, скриптов, ресурсов, шейдеров и UID; изображение/аудио и состояние исполнения этим кодовым хешем не покрываются. Вложения хранят версию при прикреплении и same_as_original; это не доказательство момента съёмки или запуска игры. Отчёты различают stale_context/stale_code/stale_feedback; у старых записей без привязки источник неизвестен. Проверки по-прежнему заявления агента.

Отключение MCP удаляет только управляемую запись выбранной игры с резервной копией, сохраняя остальные настройки. Оно не останавливает уже запущенный процесс.

Проверки регрессий: одинаковые лимиты всех записей, утверждение редакции, меньший ответ контекста, страницы длинных полей/символов, глобальные классы, Windows-разделители и запрет выхода из корня, независимые изменения заметок, более 30 попыток и чтение архивов, идемпотентность, замена решений, связанный пакет и актуальность кода, отключение одного подключения. Windows-процессы, настоящий CMD и сеансы модели с подпиской в Linux не проверяются.

## Подготовка установщика — 0.10.1

Вместо общего таймаута 15 секунд используется до 60 секунд на старт PowerShell и до 180 секунд на подготовку. Progress-файл проверяется по токену и PID дочернего процесса; чужой файл не продлевает ожидание. Он не является разрешением закрыть GUI: ready.json по-прежнему создаётся только после блокировки, SHA256 и MCP-проверок. При таймауте остаётся cancel; поздний установщик не заменяет приложение.

Перед проверкой каждого большого файла helper записывает фазу, parent показывает её в диалоге. Сохраняются exit code/signal, последний этап, ограниченные хвосты stdout/stderr и installer.log. «Скопировать диагностику» читает реальные файлы последней попытки в проверенной соседней папке; токен протокола не включается. Старое installed для другой версии не показывается как подтверждение текущей.

Если предыдущий отменённый helper ещё держит блокировку, новый ожидает её освобождения до 60 секунд с понятным этапом. Одновременная установка не разрешается. Пакет UPDATE печатает ход проверки/копирования Electron и запускается отдельно от старого кода 0.9.0. Это путь восстановления старых клиентов; изменение нового загруженного ASAR не меняет уже работающий установщик старой версии.

Проверки: 81 Node-тест, 13 PowerShell-сценариев установщика, браузер и реальный Electron. Регрессия запускает реальный PowerShell/Electron с OPORA_TEST_SLOW_PREP=1 и задержкой 9 секунд на каждую из двух проверок SHA256: прежний предел 15 секунд превышается, GUI закрывается после ready, затем подтверждается новая версия и восстановление проекта. Windows-специфичные CIM и блокировки по-прежнему требуют проверки на Windows; тест выполнен под Linux.


## Claude Code в приложении — 0.11

В верхней панели нажмите **«>_ Claude»**. Сначала выберите папку игры. Опора найдёт установленный Claude Code, настроит его проектный MCP и откроет полноценный PTY в корне выбранной игры. Если автоматический поиск не сработал, нажмите «Указать Claude» и выберите claude.exe или стандартный npm claude.cmd. Для npm нужен Node.js в PATH. Авторизация и разрешения обрабатываются самим Claude Code.

Можно открыть новую сессию, продолжить последнюю через `--continue`, скрыть панель, развернуть её и вставить текущую задачу. Вставленный запрос не отправляется автоматически: проверьте его и нажмите Enter. Ctrl+Shift+C копирует выделение, Ctrl+Shift+V вставляет текст. Горячие клавиши Опоры не перехватывают ввод терминала. Навигация и MCP-обновления интерфейса не пересоздают терминал. Смена игры и установка обновления требуют закончить работающую сессию. Закрытие приложения с работающим Claude запрашивает завершение.

Опора не сохраняет расшифровку терминала на диск; до 1 МиБ вывода хранится в памяти, xterm ограничен 5000 строками прокрутки. Claude хранит свою историю обычным способом. Вывод терминала не может менять системный буфер через OSC 52. Запуск не использует shell-строки или режим обхода разрешений. Статус «ПРОЦЕСС РАБОТАЕТ» подтверждает процесс CLI; готовность MCP проверяется в самом Claude через `/mcp`.

Приложение использует xterm.js 6.0.0, addon-fit 0.11.0 и node-pty 1.1.0. Windows N-API-файлы, ConPTY DLL и worker-скрипты находятся в app.asar.unpacked. Они включены в ZIP малого обновления отдельно от неизменяемого Electron и проверяются SHA256. Подготовка старым клиентом 0.10.1 совместима с новым ZIP. В Linux проверены настоящий Electron PTY с интерактивным тестовым CLI, 84 модульные проверки и 15 сценариев PowerShell-установщика; Windows GUI/ConPTY и реальный аккаунт Claude требуют проверки на компьютере пользователя.


## Явный запуск установщика — 0.11.1

Полученная с Windows диагностика: PowerShell PID 21016 завершился с exitCode=0 за 115 мс, без progress/ready, stdout и stderr. Обновление 0.10.1 → 0.11.0 не начиналось. Эта сигнатура отличается от долгой проверки SHA256: увеличение таймаута её не исправляет. Точная внутренняя причина раннего выхода Windows PowerShell здесь не воспроизведена.

Новый запуск использует абсолютный системный PowerShell, `-File bootstrap.ps1` и обычный дочерний процесс вместо DETACHED_PROCESS и inline -Command. Node освобождает свой дескриптор процесса через unref после готовности; файл вывода остаётся у установщика. Bootstrap до импорта библиотеки записывает PID, токен и версию PowerShell; вызов Read-UpdatePlan / Invoke-OporaUpdate явный, без эвристики MyInvocation. Неподтверждённый старт и exitCode=0 не разрешают закрытие GUI. Ошибка bootstrap сохраняет этап и причину; диагностический экспорт скрывает токен.

Малый пакет восстановления запускает UTF-8 BOM `light-update.ps1` через `-File`. ExecutionPolicy задаётся только дочернему процессу и не меняет настройки пользователя или компьютера. Для клиента с неисправным старым запуском нужен один ручной UPDATE-OPORA.cmd из свежего ZIP: заменять код уже работающего старого клиента новым архивом нельзя.

Проверки: 89 Node-тестов, 15 сценариев PowerShell, реальный перезапуск PowerShell/Electron с сохранением проекта. Нулевой ранний выход, отдельное подтверждение bootstrap, неподлинные подтверждения и ошибки загрузки покрыты регрессиями. Проверки под Linux не подтверждают работу Windows PowerShell 5.1 на компьютере пользователя.


Пакет восстановления отдельно проверен целиком через реальный -File с отключённым stdin: локальное копирование Electron, файлы терминала, резервная копия и подтверждение новой GUI. Linux-тест использует свой Electron и только флаги запуска Chromium. Проверка обнаружила сбой Start-Process для путей с квадратными скобками; запуск Opora.exe заменён на ProcessStartInfo с буквальным FileName/WorkingDirectory. Сценарий `node scripts/recovery-smoke.cjs` воспроизводит весь путь на такой папке. Он не проверяет Windows PowerShell 5.1 или блокировки файлов Windows.


## Обновления без остановки агентов — 0.12

Основной сценарий: «Обновления → Проверить и обновить». Renderer ждёт сохранения формы, очереди записей и операций с изображениями. Main проверяет канал и архив; подготовка выполняется на Node с yauzl, проверкой SHA256 приложения/нативных файлов, безопасных путей и ограничений ZIP. PowerShell не участвует в основном обновлении. Повреждение файлов Electron переключает загрузку на полную сборку автоматически.

Версии находятся в userData/runtime/<installation-id>/v/<version-id>; opora-active.json — атомарный указатель. Новая копия подготавливается при работающей старой. Неизменённые runtime-файлы связываются жёсткими ссылками, при неподдерживаемой операции копируются. Старые каталоги не перемещаются и не удаляются: действующие MCP могут продолжать читать свою версию. Базовый exe и стабильный stdio-диспетчер нужны для последующих запусков; существующие настройки MCP автоматически не переписываются. Новое подключение использует диспетчер активной версии. Старое корректное подключение остаётся зарегистрированным.

Встроенный Claude размещён в отдельном локальном PTY-процессе. GUI подключается по 127.0.0.1 к случайному порту; токен 256 бит находится только в приватном userData, каждый новый клиент проходит проверку. Ограничены размер кадров, история вывода и буфер исходящих данных; OSC 52 блокируется. Сессия и PID сохраняются при перезапуске GUI. Обычное закрытие приложения по-прежнему спрашивает о завершении Claude; обновление только отсоединяет окно.

Установщик, PTY-хост и новая GUI запускаются отдельно от группы процесса Windows. Это предотвращает их завершение вместе с прежним окном/консолью. После готовности worker main завершает передачу ввода терминала, освобождает singleton, записывает подтверждение сохранения с токеном и завершает только GUI. Worker проверяет этот переход, переключает указатель и запускает кандидат. Его окно скрыто до готовности renderer и подтверждения точной версии/PID/пути. Сбой старта возвращает указатель и запускает предыдущую версию. Зависший неподтверждённый кандидат завершается отдельно, без остановки PTY и MCP. Краткие блокировки файлов повторяются с ограниченным ожиданием. Конкурирующие установщики сериализуются.

Первый переход с 0.11.x через свежий UPDATE-OPORA.cmd тоже автоматизирован: установленный Electron выполняет migrate.cjs из отдельной папки opora-update. Он проверяет/подготавливает копию и использует системный .NET Framework для небольшого локального помощника. Помощник обращается только к GUI точного exe, сохраняет внешние MCP и не прерывает старый встроенный Claude; при такой сессии переход ожидает её обычного окончания. START-OPORA.cmd после перехода выбирает активную версию. Все эти действия выполняются без повышения прав. Старый код кнопки невозможно изменить только скачиванием архива, поэтому этот переход нужен один раз.

Проверки: 95 Node-тестов, UI/Electron/терминал, реальный сценарий по кнопке на Linux и Windows, возврат предыдущей версии, CMD-переход на Windows с сохранённым MCP, 15 PowerShell 5.1 сценариев совместимости. Windows run: https://github.com/Isedis/basket/actions/runs/42164319181. Тестовый Claude — локальный интерактивный CLI; авторизация модели и платный запрос в эти проверки не входят.
